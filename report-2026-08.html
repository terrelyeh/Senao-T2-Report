TICKET #121968326
The initial DHCP Discover from KOKOMO Cloud AP includes a Requested IP Address
Affected: KOKOMO-W220 / W222 Opened: Aug 6, 2026 Last Response: Aug 10, 2026 Closed: Aug 27, 2026
Resolved
Case Description

The customer investigated an issue in KOKOMO Cloud where IP address acquisition via DHCP occasionally failed. During packet capture analysis on the KOKOMO AP (W220/W222), they observed that even after a factory reset or in its initial default state, the initial DHCP Discover packet includes an unknown Requested IP Address (192.168.1.1 in Option 50). The customer requested clarification on why Option 50 contains this default static address during the initial DHCP state and raised concerns that certain DHCP server implementations might ignore or fail to process the request properly.

Case Summary

Support clarified that requesting a fallback static IP (192.168.1.1) via Option 50 in DHCP Discover packets originates from standard native OpenWrt framework (netifd) behavior rather than custom code. Under standard RFC 2131 specifications, compliant DHCP servers are expected to handle or ignore this hint and offer an available pool IP if the requested IP cannot be assigned. The customer acknowledged that this standard OpenWrt behavior carries a very low risk of interoperability issues and confirmed the response satisfied their inquiry, allowing the ticket to be closed.

Ticket Details
  • Address Source: The 192.168.1.1 value populated in Option 50 is the AP's factory-default fallback LAN IP address, not a residual lease from a prior network session.
  • Root Cause / Framework Rationale: In standard OpenWrt, when an interface is configured in DHCP mode with a default fallback IP (ipaddr), netifd automatically passes that static value to udhcpc as an address hint, which populates Option 50 in the outgoing DHCPDISCOVER packet.
  • Standards Compliance: Per RFC 2131 Section 4.3.1, if a server cannot fulfill Option 50, it should issue a DHCPOFFER with a different available address rather than dropping the request.
  • Packet Analysis: Packet captures revealed only outgoing DHCP Discover packets from the AP without any incoming DHCP Offer or ACK from the server side, pointing to external network/relay/VLAN path issues rather than an AP defect.

Affected: KOKOMO-W220AX-IS Opened: Aug 7, 2026 Last Response: Aug 19, 2026 Closed: Sep 14, 2026
Resolved
Case Description

On the morning of August 5, clients on a specific floor experienced Internet connectivity issues. The exact time, affected devices (MAC/serial numbers), and extent of the impact were unknown. APRESIA investigated AP cloud connectivity, client activity, signal strength, and SSID traffic logs, but found no definitive cause due to limited customer data. They requested general troubleshooting recommendations and clarification on how Client Balancing and 802.11v BSS Transition Management (BTM) work.

Case Summary

The ticket focused on clarifying the mechanisms of Client Balancing and 802.11v BTM steering rather than a specific hardware fault. Region.Support clarified that a balance log event indicates a relative client count difference (>3%) between neighboring APs rather than high AP load (which triggers under loading when client count exceeds 70% capacity). Recommendations for similar intermittent issues include collecting full event logs, analyzing client association/disassociation events, and temporarily disabling Client Balancing/Band Steering to rule out steering behavior.

Ticket Details
  • Evaluation Frequency: Every 30 seconds for 802.11v-supported clients.
  • Path 1 (reason='rssi'): Neighbor signal ≥ 10 dB stronger; target AP channel utilization ≤ 70%.
  • Path 2 (reason='balance'): Neighbor signal within 5 dB; local load exceeds target load by >3%; target channel utilization ≤ 70%.
  • Path 3 (reason='loading'): Local client count exceeds 70% of the configured radio client limit.
  • Metric Usage: Client count (as a % of configured limit) is the primary trigger. Channel utilization acts strictly as a gate (≤ 70%) for target APs, not a trigger. Airtime utilization is not measured separately.

TICKET #124673740
Troubleshooting and Log Collection Guidelines for APs in Standalone Mode
Opened: Aug 14, 2026 Last Response: Aug 17, 2026 Closed: Sep 14, 2026
Resolved
Case Description

This case addresses an inquiry from APRESIA regarding the recommended troubleshooting and log collection procedures for Access Points (APs) operating in Standalone Mode. Since Standalone Mode lacks remote PASSCODE access and an explicit "Export Log" button in the local GUI, APRESIA sought guidance on how customers should collect logs. In response, it was noted that EnGenius APs are designed with a Cloud-First architecture, making Standalone Mode suitable primarily for single-AP deployments due to the lack of multi-AP features like Fast Roaming and Auto Channel Planning. While local Event Logs can be viewed via the GUI and system logs can be exported using the Remote Syslog feature under Global Settings, standalone support relies heavily on channel partners, who must arrange local remote desktop access (such as AnyDesk) for advanced troubleshooting. Consequently, an internal feature request was submitted to the Product Line Management (PLM) team to evaluate adding a direct log export function for Standalone Mode in future updates.

Case Summary

Case Summary

APRESIA Support raised an inquiry regarding the recommended troubleshooting procedures and log collection methods for Access Points (APs) operating in Standalone Mode. Because Standalone Mode operates without cloud connectivity, support personnel cannot access the customer environment remotely using a PASSCODE, nor is there an explicit "Export Log" button in the local GUI.

The inquiry sought clarification on how to handle troubleshooting, what logs/diagnostic information customers should collect, and Senao's standard support workflow for non-cloud-managed deployments.

Key Discussion Points & Findings

  • Deployment & Technical Limitations:
    • Multi-AP Constraints: Standalone Mode is not recommended for deployments with more than one AP. Key cloud-managed features—such as AP-to-AP communication, Fast Roaming, and Auto Channel Planning—are unavailable or impaired in Standalone Mode.
    • Cloud-First Architecture: EnGenius / KOKOMO APs are designed primarily as Cloud-First devices. Standalone deployment options are intentionally limited in terms of centralized management and remote diagnostic access.
  • Available Diagnostic Options in Standalone Mode:
    • Local Event Log: The Event Log display remains accessible via the AP's local web GUI.
    • Remote Syslog: Technical teams can configure the Remote Syslog function under Global Settings to offload system logs to an external syslog server.
  • Support Escalation & Handling Workflow:
    • Channel Partner Responsibility: Standalone mode deployments are primarily maintained by channel partners/integrators.
    • Remote Access Requirement: For deeper on-premise troubleshooting, channel partners or end-users are typically requested to provide temporary remote desktop access (e.g., AnyDesk) to a local host within the AP's network segment.
