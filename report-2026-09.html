TICKET #130309642
Cloud-Dependent Features and Their Behavior When Cloud Connectivity Is Lost
Affected: ALL KOKOMO Model Opened: Sep 4, 2026 Last Response: Sep 4, 2026 Closed: Sep 4, 2026
Resolved
Case Description

Apresia Support inquired about the behavior of cloud-dependent features when an Access Point or network device loses connectivity to the cloud service. Specifically, they asked whether features like Client Access Control operate in a "Fail Open" or "Fail Close" state during an outage, and requested a comprehensive list of cloud-dependent features along with their respective behavior when offline.

Case Summary

Tier 1 Support (APRESIA) submitted a request to clarify offline device behavior for cloud-managed features. Tier 2 Support (Region.Support) clarified that only Captive Portal and EnGenius Cloud RADIUS are strictly cloud-dependent. Features such as My-PSK, Access Control Lists (ACLs: Allowlist and Blocklist), and Firewall rules continue to function offline based on the last synced configurations cached locally on the device. Satisfied with this clarification, Tier 1 closed the ticket.

Ticket Details

Initial Inquiry (Sep 4, 2026): 水谷@KOKOMOSupport submitted a structured technical inquiry asking which features rely on active cloud connectivity. Specifically using Client Access Control (Blocklist) as an example, they asked whether the system defaults to "Fail Open" (allowing all clients) or "Fail Close" (denying all clients) when offline, and requested a full list of cloud-dependent features and their offline behavior.

  • Initial Response by Region.Support: Region.Support clarified that per specification, only Captive Portal and EnGenius Cloud RADIUS are cloud-dependent features. Other features—including My-PSK, ACL (Allowlist and Blocklist), and Firewall rules—continue to function normally even when devices lose cloud connectivity because their configurations are synchronized to the local device level rather than executing on the cloud controller.
  • Clarifying Follow-up by 水谷@KOKOMOSupport: To ensure full clarity regarding ACL Blocklists, 水谷@KOKOMOSupport re-queried what happens to a client already on the block list trying to connect while the AP has lost internet connectivity.
  • Detailed Technical Explanation by Region.Support: Region.Support explained that the ACL Client MAC list is saved locally on the AP/Switch upon every cloud sync.
  • If a device (Client A) was on the blocklist during the last successful sync, the AP will continue enforcing the block using its cached configuration while offline.
  • If an administrator removes Client A from the blocklist in the cloud while the AP is offline, the AP cannot receive the update and will continue operating on the last cached rule (keeping Client A blocked) until cloud connection is restored.
  • APs do not query the cloud live for every client connection; all ACL and My-PSK policies are stored and evaluated locally.
  • The "Configuration" column in the cloud UI allows administrators to identify which devices have up-to-date configs vs. outdated/un-synced cached configs.

TICKET #130077608
KOKOMO Switch & Standalone AP
Affected: KOKOMO Switch & Standalone AP Opened: Sep 3, 2026 Last Response: Oct 20, 2026 Closed: Oct 20, 2026
Resolved
Case Description

The submitter inquired about the behavior and specifications of the "Command line Save / Restore only" feature during local GUI Backup/Restore operations on KOKOMO switches and upcoming standalone APs. Specifically, they requested verification on observed file formats (.csr text format when Enabled vs. .cfg binary format when Disabled), restore success/failure conditions, password masking behavior, and a comprehensive list of system settings excluded from backup files (such as encryption keys, certificates, SSH host keys, and banner files).

Case Summary

Tier 1 Support (APSSup / 高松＠KOKOMOSupport) sought specification verification regarding Backup/Restore file formats and excluded configuration parameters. Tier 2 Support (Region.Support) detailed the pairing rules (Enabled ↔ .csr, Disabled ↔ .cfg) and clarified that passwords are masked in plain-text .csr files. Additionally, Tier 2 provided a list of parameters included and excluded from AP/Switch backups. After briefly closing the ticket, Tier 1 reopened it to request further clarification on whether excluded items (Certificates, SSH host keys, Banner files, and Encryption Keys) can be configured via GUI or are managed internally by system firmware, which is currently under R&D review.

Ticket Details

Initial Inquiry by APSSup (Sep 3, 2026): Summarized test results on KOKOMO switch backup/restore:

  • Backup: Enabling "Command line Save / Restore only" generates a .csr text file; disabling it generates a .cfg binary file.
  • Restore: Restoring .csr fails when Disabled. Restoring .cfg succeeds under both settings, but LSP login passwords only restore when using .cfg with the setting Disabled.
  • Asked Tier 2 to verify these test findings, explain the feature's scope, and list all settings excluded during restore.
  • Technical Explanation by Region.Support:
    • Neither .csr nor .cfg files include Encryption Keys, Certificates, SSH host keys, or banner files; these remain preserved on the device hardware.
    • .csr (plain text) can be edited and is not locked to a specific model, though non-applicable commands fail individually upon apply. .cfg is model-restricted via file header validation.
    • Password fields in CLI text format (.csr) are masked for security and cannot be restored from .csr. Passwords/accounts require a .cfg backup with the setting Disabled.
    • Restoring .csr while Disabled fails by design due to binary header checks. UI improvements will be requested to block mismatched file extensions.
    • Emphasized that file formats must strictly match the setting: Enabled ↔ .csr and Disabled ↔ .cfg.
  • Follow-up Queries on Device Replacement & Standalone AP by 高松＠KOKOMOSupport:
    • Asked if replacing a failed switch requires restoring via Disabled ↔ .cfg and manually reconfiguring excluded items (certificates, SSH host keys, banner files).
    • Asked about the upcoming Standalone AP GUI (which uses a single backup file type) and whether it similarly excludes certain device-retained settings.
  • Detailed Standalone AP Guidance by Region.Support:
    • Confirmed standalone AP configurations can be restored, including management credentials and SSH host keys, but cross-model restore is not supported and performing a factory reset before restore is recommended.
    • Included in AP backup: /etc/config, management credentials, SSH host keys.
    • Excluded from AP backup: Certificates, banner files.
  • Reopening & Clarification Request on Excluded Settings by 高松＠KOKOMOSupport:
    • Closed the ticket initially, but reopened it shortly after to clarify GUI configuration locations.
    • Stated they could not locate GUI fields for Certificates, SSH host keys, Banner files, or Encryption Keys in Switch LSP or Standalone AP GUI.
    • Asked whether these excluded items are internally auto-generated/managed by the system rather than user-configurable GUI fields, and requested a definition of "Encryption Keys."
TICKET #130917910
Please explain how "Freeze Firmware Version" works
Affected: KOKOMO Cloud Managed Devices Opened: Sep 6, 2026 Last Response: Oct 20, 2026 Closed: Oct 20, 2026
Resolved
Case Description

The submitter requested detailed specification clarifications regarding the "Freeze Firmware Version" feature on KOKOMO Cloud. Specifically, they inquired about the device firmware synchronization process, downgrade/upgrade behaviors, and "Force Offline" policy implications when replacing a failed hardware unit (RMA) assigned to a network frozen on a legacy firmware version that is no longer listed under Beta, Stable, or Previous Stable releases.

Case Summary

Tier 1 Support (APSSup / 峯村@KOKOMOSupport) submitted a multi-part inquiry to understand how replacement devices behave when assigned to a network set to an unlisted, frozen firmware version. Tier 2 Support (Region.Support) clarified that firmware synchronization follows standard network rules (Forced vs. Bypass under Initial Auto-Firmware Upgrade), that replacement units will successfully upgrade/downgrade to the frozen version even if unlisted, and that EnGenius Cloud does not enforce automatic offline locks based on generation age. Satisfied with these technical explanations, Tier 1 closed the ticket.

Ticket Details

Initial Inquiry by 峯村@KOKOMOSupport: Submitted a detailed 6-question inquiry asking what happens when a device on a frozen legacy firmware version (e.g., 3 generations old, no longer listed under Beta/Stable/Previous Stable) fails and needs replacement:

  • Can the replacement device download and install the frozen version upon syncing with the Cloud?
  • Are there downgrade restrictions if the replacement unit arrives with the latest factory firmware?
  • Does a version causing a "forced offline" state prevent configuration/firmware sync?
  • Does a replacement unit sync its configuration/firmware first before being forced offline?
  • How large of a version gap triggers a forced offline state?
  • What are the historical examples or policy criteria (e.g., N-generations behind rule) for forcing devices offline?
  • First Response by Region.Support:
    • Clarified that RMA replacement units follow standard network firmware synchronization mechanisms based on Configure → Firmware → Advanced Settings → Initial Auto-Firmware Upgrade:
    • Forced: Device immediately upgrades/downgrades to the target frozen firmware.
    • Bypass: Device waits for the configured maintenance window before syncing.
  • Confirmed that replacement devices will attempt to sync to the target frozen version upon joining the network, but noted that the specific behavior for unlisted legacy releases and Q3/Q6 was under further check.
  • Follow-up Query by 峯村@KOKOMOSupport: Re-iterated the importance of understanding the behavior of unlisted frozen firmware versions and requested explicit answers for Q3 and Q6.
  • Detailed Policy Explanation by Region.Support:
    • Q3 (Sync vs. Force Offline): Clarified that synchronization proceeds normally. Standard version aging does not trigger a forced offline state. Older releases do not trigger offline locks, so replacement units successfully connect, download the target frozen firmware, apply configurations, and remain online.
    • Q6 (Historical Cases & Criteria): Confirmed there are no historical cases of devices being forced offline due to version age. There is no "N-Generations Behind" rule (e.g., 4 versions behind does NOT force an offline state). The "Force Offline" safeguard is reserved strictly for extraordinary security events (e.g., critical zero-day vulnerabilities or protocol-breaking infrastructure changes).
  • Clarification Confirmation by 峯村@KOKOMOSupport: Asked Tier 2 to explicitly confirm the single remaining item: whether a replacement unit will successfully upgrade or downgrade to an unlisted frozen firmware version.
  • Direct Confirmation by Region.Support: Explicitly confirmed with "YES, the device will upgrade/downgrade the FW to the Freeze FW Version."

  • Blocking the documented IP (35.79.186.153) still allowed client authentication.
