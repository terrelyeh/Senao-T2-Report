TICKET #120151159
Specifications for VIP lists and L2 isolation
Affected: Kokomo Cloud Opened: Jul 30, 2026 Last Response: Aug 7, 2026
Open
Case Description

Kokomo Support seeks confirmation on two technical points regarding the VIP List feature and Layer 2 (L2) Isolation on the Access Point:

  • Relationship Between VIP List and L2 Isolation: Whether disabling Layer 2 Isolation is merely a recommended practice for common use cases (e.g., enabling client devices to communicate with printers or IoT devices on the VIP List) rather than a strict functional requirement of the VIP List feature itself.
  • Standard Client Devices on VIP List: Whether standard client devices (such as PCs) can be added to the VIP List while keeping Layer 2 Isolation enabled without causing operational issues.
Case Summary

This ticket (#120151159 • Specifications for VIP lists and L2 isolation) involves an inquiry by 健心 regarding the VIP List feature and Layer 2 (L2) Isolation behavior on the AP.

Reason for Inquiry:

  • Technical Clarification: To confirm whether disabling L2 Isolation is a strict functional requirement of the VIP List feature or merely a recommended setup for specific use cases (such as allowing wireless clients to communicate with a network printer).
  • Logging Issues: To address a bug where no Captive Portal log entries were recorded for specific devices on Guest Wi-Fi, affecting visibility into device authentication.

Key Findings:

  • Feature Compatibility: Disabling L2 Isolation is not a requirement. L2 Isolation (which blocks local client-to-client traffic) and the VIP List (which controls network access/bypass for captive portal) operate independently and can be used together.
  • Standard Device Support: Standard devices like PCs can be placed on the VIP List while L2 Isolation remains enabled without issue.
  • Automatic Authorization & Logging: VIP wireless clients do not need to interact with a Splash Page, as authorization is handled automatically upon association. Once authorized, the Event Log should record a "Captive Portal User Login" event using the client's MAC address as the username.
Ticket Details

Ticket Details

  • Ticket ID & Title: #120151159 • Specifications for VIP lists and L2 isolation
  • Requester: 健心 (Mizutani / KOKOMOSupport)
  • Platform & OS: Windows (Always reproducible)
  • Category: AP (Access Point)

Full Narrative Description

Background & Core Technical Questions

The inquiry was submitted by 健心 to clarify the technical relationship between the VIP List feature and Layer 2 (L2) Isolation on Access Points:

  • VIP List vs. Layer 2 Isolation Requirement:

The VIP List is designed for head-less devices (printers, scanners, IoT equipment) that lack a user interface to enter Captive Portal authentication credentials. The requester sought to confirm whether disabling L2 Isolation is merely a best-practice recommendation (allowing clients to communicate directly with local devices like printers) rather than a hard technical requirement of the VIP List feature itself.

  • Standard Clients on VIP List:

Confirmation was requested on whether a standard client device (e.g., a PC) can be added to the VIP List while keeping L2 Isolation enabled on the SSID without causing operational issues.

Reason for Performing This Work

  • Technical Clarification: To verify the independent operation of L2 Isolation and Captive Portal VIP Lists for network design accuracy.
  • Troubleshooting a Logging Issue: To investigate a reported bug where no Captive Portal log entries were recorded for specific devices on Guest Wi-Fi, preventing proper visibility into device authentication history.

Findings & Discoveries

  • Feature Independence: Disabling L2 Isolation is not a requirement for the VIP List. L2 Isolation (which controls client-to-client traffic on the local network) and the VIP List (which controls external network access and Captive Portal bypass) operate independently and can be used simultaneously.
  • Standard Device Support: Standard devices (such as PCs) can be registered on the VIP List while L2 Isolation remains enabled without issue.
  • Automatic Authorization: VIP wireless devices bypass the manual Splash Page prompt entirely; authorization occurs automatically upon network association.
  • Logging Behavior: Upon successful authorization, the Event Log records a "Captive Portal User Login" event, using the client's MAC address as the username.
  • Root Cause of Missing Logs: R&D discovered that after explicitly enabling the VIP feature on the Guest Wi-Fi SSID, Captive Portal entries appeared properly in the authentication history.

TICKET #113577076
Could you clarify the mesh functionality?
Opened: Jul 2, 2026 Last Response: Jul 7, 2026 Closed: Jul 7, 2026
Resolved
Case Description

Kokomo Support is asking to confirm the technical behavior of the mesh feature in KOKOMO Cloud when only a single frequency band is enabled.

Questions:

  • Client-Facing SSID Connectivity: Does enabling mesh on a single frequency band only specify the backhaul band (while automatically providing mesh connectivity across all frequency bands for client SSIDs), or is mesh restricted exclusively to the enabled frequency band for client devices?
  • Dedicated Mesh Backhaul Configuration: Can a specific frequency band (e.g., 6 GHz) be dedicated exclusively to mesh backhaul by disabling 6 GHz on all client-facing SSIDs while enabling mesh on the 6 GHz band?
Case Summary

The ticket (#113577076) clarifies how mesh functionality and frequency bands work in KOKOMO Cloud across three main points:

  • Mesh Compatibility & Frequency Band Selection: Mesh functionality is supported only between Kokomo APs (not third-party APs). The mesh backhaul operates on the frequency band selected on the Global Radio Page. For backhaul over 6 GHz, all meshed APs must support 6 GHz (e.g., a W220AX-IS cannot mesh with a KOKOMO-W222BE-IS over 6 GHz).
  • Dedicated Mesh Backhaul (6 GHz): To dedicate 6 GHz exclusively for mesh backhaul on the KOKOMO-W222BE-IS, a user can enable 6 GHz for mesh while setting SSIDs to broadcast only on 2.4 GHz and 5 GHz.
  • Simultaneous Backhaul and Client Traffic: If an SSID is broadcast across all bands (2.4/5/6 GHz) and 5 GHz is set as the mesh backhaul, the 5 GHz radio will simultaneously handle both mesh backhaul traffic and direct client communications.
Ticket Details

Initial Inquiry (Jul 2, 2026)

峯村@KOKOMOSupport opened the inquiry with two specific technical questions regarding KOKOMO Cloud, noting that only one frequency band can be enabled for the mesh feature at a time:

  • Band Scope: Does selecting a specific frequency band for mesh only define the band used for the mesh backhaul (while client-facing SSIDs continue to provide mesh connectivity across all bands), or is mesh restricted strictly to the selected band for client devices?
  • Dedicated Backhaul: Can a user dedicate a specific frequency band (such as 6 GHz) exclusively to the mesh backhaul by disabling 6 GHz across all SSIDs while enabling mesh on the 6 GHz band?

First Response & Clarification

Region.Support replied to address the inquiry and clear up key parameters:

  • Mesh Compatibility: Only KOKOMO APs can form a mesh network with other KOKOMO APs; third-party APs are not supported.
  • Mesh Backhaul: The mesh backhaul is established using the radio band selected on the Global Radio Page.
  • 6 GHz Mesh Setup: Enabling mesh on the 6 GHz band requires using all 6 GHz-capable APs (such as the KOKOMO-W222BE-IS). Users can indeed dedicate the 6 GHz radio to mesh backhaul while restricting client SSIDs to the 2.4 GHz and 5 GHz radios.

Follow-Up Question

峯村@KOKOMOSupport thanked the support team for clarifying compatibility with third-party APs and followed up with a third point:

  • Shared Band Utilization: If an SSID is broadcast across all bands (2.4 GHz, 5 GHz, and 6 GHz) and 5 GHz is selected as the mesh backhaul, will the 5 GHz radio handle both mesh backhaul traffic and client communications simultaneously?

Final Confirmation & Ticket Closure

Region.Support confirmed:

  • Yes. The 5 GHz radio will serve both mesh backhaul traffic and active client communications simultaneously when configured this way.

峯村@KOKOMOSupport confirmed that the explanations resolved all questions and requested to close the matter. The ticket was then marked as resolved and closed.
