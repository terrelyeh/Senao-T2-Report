TICKET #94722952
How to Identify Applications
Affected: KOKOMO-W220AX-IS Opened: Apr 22, 2026 Last Response: Apr 24, 2026 Closed: Apr 24, 2026
Resolved
Case Description

We would like to inquire about how application identification is performed for the applications displayed on the dashboard screen.

For example, even though we are using Microsoft Teams, the application display sometimes shows "Skype_TeamsCall". What specific information does the AP use to identify applications?

Case Summary
  • Application identification on the AP is performed using nDPI v4.6, an open-source Layer 7 Deep Packet Inspection (DPI) library, not the chipset SDK.
  • Microsoft Teams traffic may appear as Skype_TeamsCall because Teams reuses Skype's real-time media stack, and nDPI shares the same fingerprint definitions for Teams/Skype voice and video traffic.
  • nDPI identifies applications using multiple methods including packet payload inspection, ports, IP addresses, TLS certificates, SNI information, and known service IP lists.
  • Application classification is performed on a per-flow / per-session basis, meaning different traffic types from the same application can appear differently (e.g., Zoom media traffic as Zoom, but encrypted file transfer traffic as TLS).
  • TLS classification means the encryption protocol was identified but the actual application could not be determined, while Others/Unknown means nDPI could not identify the traffic or protocol at all.
TICKET #90835276
About Firewall-Rule
Affected: KOKOMO-W220AX-IS Opened: Apr 10, 2026 Last Response: Apr 13, 2026
Open
Case Description

We would like to ask about the firewall rules required to bring the access point (AP) online. We reviewed the following documentation: https://docs.lan.kokomocloud.com/appendix/firewall-rule

Based on this document, we configured the proxy server to allow only *.production.kokomocloud.com. However, the AP does not come online.

We suspected that NTP might be related, so we also verified the NTP allow configuration. Based on our verification, NTP does not appear to affect whether the AP becomes online or not.

We have confirmed that:

  • When all outbound communications are allowed, the AP successfully comes online.
  • DNS and HTTP/HTTPS server settings are already configured on the AP.

We would appreciate your clarification on the following two points:

  • Is it acceptable to consolidate the required FQDNs using a regular expression (for example, *.production.kokomocloud.com) when defining allow rules on a proxy server? We understand that this may depend on the proxy server implementation.
  • Could you please advise the minimum set of FQDNs that must be allowed in order for the AP to come online?
Case Summary
  • Issue: AP does not come online when only *.production.kokomocloud.com is allowed through the proxy/firewall, but works normally when all outbound traffic is permitted.
  • NTP: Tested and does not appear to affect the AP online status. DNS and HTTP/HTTPS settings are already configured correctly on the AP.
  • Customer Question 1: Whether wildcard/regex rules such as *.production.kokomocloud.com are officially supported for proxy allow rules.
  • Customer Question 2: The minimum required FQDN/domain list and any additional requirements needed for AP cloud connectivity.
  • Next Steps: Region.Support requested confirmation that TLS/SSL inspection is not being modified by the proxy and asked for a reproducible test environment or remote access (AnyDesk/passcode) so R&D can investigate which service or destination is being blocked.
TICKET #89654522
About Log Information
Opened: Apr 6, 2026 Last Response: Apr 9, 2026
Open
Case Description

[Background]

An issue occurred in which a wireless client was temporarily unable to obtain an IP address via DHCP. The access point is operating in bridge mode with a static IP address, and DHCP is provided by an on-premises (internal) server.

[Question]

Is it possible to investigate this issue using logs available in the cloud? For example, AP logs or a client activity timeline.

As part of our verification, we intentionally denied DHCP OFFER packets to simulate the behavior; however, no information indicating the root cause could be identified from the cloud-side logs.

Case Summary
  • Scenario: A wireless client temporarily failed to obtain an IP address via DHCP in an environment where the AP operates in bridge mode with a static IP, while DHCP is provided by an internal server.
  • Customer Question: Whether the issue could be investigated using cloud-side information such as AP logs or client activity timelines.
  • Test Result: During testing, DHCP OFFER packets were intentionally blocked to reproduce the issue, but no clear root-cause information was visible in the cloud logs.
  • Explanation: Since the DHCP OFFER deny did not originate from the AP itself, the AP logs would not record this event.
  • Recommended Troubleshooting: Use Wired Packet Capture in Diag Tools during authentication/DHCP exchange, and check switch configurations — especially DHCP Relay settings and MAC learning limits on switch ports — as similar cases have been observed before.
